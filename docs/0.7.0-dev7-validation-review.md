# CSR2-CDN 0.7.0.dev7 — validation fixes and limits

This revision responds to the operator's October 15 dev6 validation report.
The report established successful metadata retrieval, but only standalone
historical Showdown coverage and a repeated session identity mismatch before
crew reads. The 345 previous offline tests passed; no service reads succeeded.

## Automatic event discovery (offline implementation)

- Read the current, versioned AssetDatabase from the normal CSR2 CDN client.
- Find common event assets using the APK-traced numeric type 47; do not match
  bundle names or hardcode specific events.
- Download only ASTC-quality bundles using bounded streaming (128 MiB per
  bundle, 512 MiB total by declared size; no binary files written).
- Parse Unity assets with UnityPy. Inspect TextAsset JSON and MonoBehaviour
  type-tree data, extracting records with explicit EventGroupName and
  associated schedule/leaderboard-definition arrays when present.
- Preserve standalone entries with duplicate names or IDs and reject
  ambiguous and malformed runtime data. Missing/stripped Unity type trees,
  undecodable assets, or incomplete catalogue retrieval are *errors* and are
  never interpreted as zero active Showdowns.
- The existing full-name-to-four-input-to-board derivation is reused;
  users supply only a PlayerID and Showdown name.

**Unverified:** No true type-47 Unity bundle was supplied in this turn and
container network access is unavailable. MonoBehaviour typetrees may be
stripped or use a different wrapper. The exact native asset serialization,
current event eligibility, and server acceptance must be tested in the
operator's authorized environment. If type trees are stripped, offline
IL2CPP type-tree reconstruction will be necessary.

## Session handling

The latest live report says the token claim did not match the PlayerID for
two selected accounts. The code retains strict validation. If the normal
portal selection yields a mismatch, a bounded second request tries a direct
PlayerID selection with its corresponding security hash. A successful HTTP
response alone never authorizes crew or leaderboard access; *both* paths
require the returned token identity to match the requested PlayerID. Errors
are sanitized and no credentials or raw account messages are logged or
persisted. Whether this alternate profile is accepted by production has not
been established.
