# Dev32 — source-only rim reference graph, not wheel-name matching

## Scope and original source evidence

The operator's separate Dev30 online report and replay confirmed release branch `6_8_0_Release`, database `33927`, six unauthenticated public GETs for source capture and zero replay requests. All four source SHA-256 values matched Dev29. It counted 480 rim records, 355 with explicit `CompatibleCars` arrays, 1,716 compatibility-string occurrences, 27 distinct compatibility strings, 138 root `CarNames` entries (four duplicate *occurrences*) and 134 `DefaultRim` entries. It found zero lexical matches among the three previously tested namespace pairs, including case-insensitive and punctuation-insensitive comparisons.

**Those aggregate reports do not contain the original cached UnityFS bundles.** No Dev32 graph results for the real 480-row source are asserted in this release. The local tests here exercise *synthetic sources only*. The operator can recompute the new counts from the previously saved original Dev30 source cache without contacting the CDN or the game.

## What Dev32 adds

`csr2cdn.dev27_native_wheel_forensics.audit_tuner_rim_source()` now emits additive source-only fields:

- `source_relationship_topology`: number of rim records with/without nonempty `CompatibleCars`, distinct nonempty compatibility sets and reused sets; distributions of distinct references per rim and rim records per reference; number and size buckets of **co-occurrence** components (two reference strings are in the same component if connected through one or more *common rim records*); root `CarNames` and `DefaultRim` multiplicity histograms; adjacent repetitions of root car names.
- `supplementary_rim_field_shapes`: bounded counts-only lexical profiles of per-rim `BrandName` and `Category`, plus number of distinct (brand, category) combinations. These are existing declared native source fields, not newly decoded eligibility tables.

These are structural *relationships within a single source*; a common rim record does not prove that two `CompatibleCars` tokens identify the same model, and a shared string shape does not establish a roster wheel-to-rim mapping. The original arrays **are not** position-wise joined; numerical coincidences like 134 distinct root names / 134 default strings remain unverified. None of the local code publishes strings, numeric source IDs, model names, token hashes, per-record joins, or the original bundles.

## Offline operator replay

With the operator's existing `public-source-cache` directory containing original source files and `manifest.json`:

```bash
python -m csr2cdn.dev30_public_source_replay \
  --replay-dir ./public-source-cache \
  --baseline-audit public-source-audit.json \
  --output dev32-offline-replay.json
```

The command name remains `dev30_public_source_replay` for backward compatibility. Use a new output filename; it never overwrites. It performs **zero** network/gameplay reads. To inspect the new fields, look under `audited_slots.rim.source_relationship_topology` and `audited_slots.rim.supplementary_rim_field_shapes` in the resulting JSON.

## Trust / release status

The public sources alone do not identify the eleven historically unresolved paint/interior *roster* entries, nor establish semantics for `IncludeToCar`, native roster wheel strings, default rim positional associations, or in-game appearance. No mappings were promoted, pruned, published or changed. This is an investigation build, **not** a release candidate. The production visual library loader and TNR decoder are unchanged.
