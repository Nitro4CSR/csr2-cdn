# 0.7.1.dev2 — optional crew/member stats and roster vehicle data

Development only. **No new game-service endpoints. No authenticated network
requests were made while building this version.** Everything below represents
observed wire keys or an experimental range, not established value semantics.

## Added typed data

`CSR2Services.get_crew_optional_snapshot()` uses **exactly two established
read-only calls**: own-crew and roster. It returns a `CrewOptionalSnapshot`
containing `CrewOptionalStats` and per-member `CrewMemberOptionalStats` and
`CrewMemberVehicle`, with a typed `CrewVehicleGacha` when the recognized
nested keys exist. The same decoding is also available offline via
`CrewOptionalSnapshot.from_reads(OwnCrew.from_response(...),
CrewMembers.from_response(...))`.

Native-observed exact wire keys used for own crew: `crew_level`,
`crew_level_base`, `crew_level_threshold`, `crew_rp`, `crew_rr_point`,
`crew_garage_value`, `crew_career_earning`, `members`, `max_members`,
`total_invites`, `total_requests`.

Native-observed roster fields: `garage_value`, `career_earning`,
`cash_donated`, `collections_rank`, `season_pass_rp_boost`,
`season_pass_premium_plus_pass_holder`, `current_car`, `car_pp`, `car_ep`,
`car_elite_level`, `car_am_milestone_level`, `car_restoration_status`,
`car_source`, and `car_gacha_config` with `caid`, `inid`, `livid`, `lzsid`,
`paid`, `whbn`. `car_tnr_setup` is only reported as an object-presence and
bounded field count; its opaque contents are never exposed by this model.

Unknown values are **not** filled with zero. Counters accept only true
nonnegative JSON integers (not bool, negative, float, numeric string).
The larger own-crew `crew_rp` is **not seasonal GCC RP**. `career_earning`,
RP boosts, progression and visual customization codes have provisional
semantics. External account identifiers and `last_log_in_time` are deliberately
not promoted to this optional model.

## Combined offline-first validation

```bash
python -m csr2cdn.crew_bulk_validation
```

Default: zero requests; prints proposed one-round contract. A future
**explicitly authorized** run is:

```bash
python -m csr2cdn.crew_bulk_validation --execute --top 20 --before 10 --after 10 --offset 0 --show-stat-values
```

The command prompts privately for PlayerID and makes exactly **four reads**:

1. `crews/checkUserCrew` (own crew)
2. `crews/viewMembers` (roster)
3. `leaderboard/crew-champs-v2/viewcrew` (published common range)
4. Same GCC path once with the explicit exploratory range

No automatic paging, repeated polling, raw JSON persistence or writes. Crew
statistics and vehicle coverage appear even if exploratory GCC decoding fails.
The common GCC read is compared to the expanded read by exact ID in memory;
completeness and offset semantics remain unverified. A complete roster can
also be checked against GCC score and garage aggregation.

For a local replay with already-captured replies, supply all four of
`--own-json`, `--members-json`, `--gcc-common-json`,
`--gcc-experimental-json`. Offline fixtures may contain private data; the
report sanitizes output but the caller controls storage and access.

**Privacy:** default report shows only field-presence/counts, guarded
comparisons, rank/score for an exact matched crew, and overlap counts.
`--show-stat-values` exposes crew scalar values plus aggregate member
statistics. `--show-members` separately opts into printing names, individual
stats and car details (never player IDs or account tokens).
`--print-gcc-entries` opts into printing returned crew names/ranks/scores.
Do not publish opt-in outputs without review.
