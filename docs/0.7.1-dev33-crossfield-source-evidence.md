# Dev33 — native rim cross-field evidence (source-only replay)

## Evidence and limits

The supplied Dev30 online and offline reports concern public branch `6_8_0_Release`, database `33927`; four validated SHA-256 sources and the public index matched Dev29. On those original source bytes the three previously tested lexical namespace comparisons found **zero** exact, case-insensitive or punctuation-insensitive matches. The earlier report counted 480 rim records, 355 with explicit `CompatibleCars`, 27 distinct compatible reference strings, 138 root `CarNames` entries including four duplicates and 134 root `DefaultRim` entries. These counts are an operator-provided baseline, **not** newly remeasured by Dev33.

The original 4 ASTC binaries and the real Dev32 topology replay were not supplied here. This build makes **no real-source claims** about the new cross-field metrics. Offline regression fixtures are synthetic.

## New source-only cross-field profile

`audited_slots.rim.source_crossfield_relationships` aggregates declared `BrandName`, `Category` and `CompatibleCars` fields from each fully validated canonical primary Tuner Stars rim record. Each native `(BrandName, Category)` tuple is treated only as an **uninterpreted grouping key**:

- number of native brand/category groups with and without nonempty compatible references;
- distinct compatible references occurring in exactly one group versus several groups;
- degree buckets of groups per reference and references per brand/category group;
- repeated compatible-reference sets that appear in multiple rim groups;
- counts of blank declared brand/category strings.

Original strings, numeric IDs, hashes of source names, per-record links, examples and model keys are not exported. The routine validates input bounds and dimensions. These counts do **not** prove `CompatibleCars` means vehicle compatibility, nor any semantic relationship between root `CarNames`, root `DefaultRim`, rim names and roster wheel strings.

## Baseline honesty fix

The replay baseline comparison previously set `matching_source_hashes_confirm_same_bytes_not_eligibility=true` unconditionally, including for mismatching baselines. Dev33 corrects this. It is true only if **all** of these agree: validated public-audit status, branch, database version, public-index SHA-256, exact requested-slot coverage and the SHA-256 of every source in the replay. Individual booleans and an `all_reported_source_bytes_and_index_match_baseline` result are provided. Mismatch is evidence divergence, never a reason to change names.
