## Prestige Cup: last live feature-validation gate

Dev16 already retrieved **21 Prestige entries** using an independently resolved source-backed board. That prior success is preserved, not rerun in Dev32. Score units, rank accuracy, stable player identity matching and the range behavior have not yet been validated against a contemporaneous game UI snapshot. The native Prestige leaderboard definition refers to `FastestHalfMileTime`, `Best`, `Ascending`; numeric scores must **not** be called RP unless proven independently.

New CLI, defaulting to zero-network dry-run:

```shell
python -m csr2cdn.prestige_release_validation
```

For an authorized live test of a fully resolved board (example ID is season 277, must be independently reconfirmed before use):

```shell
python -m csr2cdn.prestige_release_validation --execute \
  --board evnt-off-82-dur-168-hours-asc---427700000 \
  --print-entries --range-cross-check
```

Alternatively resolve the current board from the same native/metadata inputs, rather than guessing its ID:

```shell
python -m csr2cdn.prestige_release_validation --execute \
  --season 277 --car-tier 5 \
  --car-key Porsche_Manthey911GT3RSRewardRecycled_2024 \
  --print-entries --range-cross-check
```

Season number, tier and car key **must be reconfirmed from the in-game active event before testing**. Runtime resolution validates the Prestige template, selected seasonal car and leaderboard definition. It is still possible for the actual live service to reject the derived board, which should be reported as an unresolved live gate. The PlayerID is entered through a hidden interactive prompt, not a command line argument. No authenticated response bodies, player IDs or auth secrets are printed.

`--print-entries` opts in to names/ranks/scores (review locally before sharing). `--ui-rank` and `--ui-score` accept an optional **recent personal** in-game UI comparison; these are reference snapshots, never automatically certified. Omit `--ui-score` if the game displays a different unit/scaling than the numeric server response. Do not treat an apparently close score as verification of its units.

The primary read uses `StandingRange.common()` (native top 10, before 5, after 5), and the optional **second** service read uses `StandingRange.top3_and_you()` (top 3, before 0, after 0). For auto-resolution, both reads use the same resolved board ID and server result offset; metadata/CDN discovery may itself require read-only download requests. Cross-range comparisons are **sequential**, not atomic, and only compare rows that share an exact `player_uid`. If no stable identifiers overlap, the report says so. This only tests two native ranges; it does **not** establish cursor-based or arbitrary paging.

### Required evidence for Prestige acceptance

1. Live report returns decoded ranks/scores and a valid board, not just HTTP success.
2. A nearby-in-time in-game Prestige UI check confirms the rank and interpreted score/time of at least the authenticated player (or other uniquely matched entry).
3. The optional range cross-check either agrees on stable overlapping entries or reports an interpretable live-timing difference; no inferred identity matching by player names.
4. Document the intended supported Prestige scope (top/global and player-neighborhood window); arbitrary pagination is explicitly out of scope unless separately tested and promised.
