# Dev29: read-only crew endpoint data inventory (no live execution yet)

## Scope and motivation

Dev28's published Crew RP models intentionally surfaced only selected known fields. This Dev29 diagnostic examines **the same three 6.8.0 authenticated read-only responses** without fetching any new leaderboard page or discovering speculative endpoints:

1. `crews/checkUserCrew` — own-crew response, including the original envelope.
2. `crews/viewMembers` — raw roster envelope, selected member-array container, and coverage across member dictionaries.
3. `leaderboard/crew-champs-v2/viewcrew` — original GCC progress envelope and `scores` array, including one-level `logo` field names/types.

The read-only service method is `CSR2Services.get_crew_endpoint_inventory(show_stat_candidates=False)`. It requests the three existing responses in order using the same signed request builders as Dev28. Authentication uses `allow_network=True` explicitly. The CLI will not read the network unless `--execute` is supplied. No response JSON, PlayerID, tokens, crew IDs, nicknames, or individual values are saved or printed. The service instance keeps data in memory only until returned; the report contains only aggregates and permitted field names/types.

## Run modes

Dry run, **zero network calls**:

```console
python -m csr2cdn.crew_endpoint_inventory
```

After you decide to do the **next single authorized live pass** (not part of Dev29 preparation), run from an interactive terminal:

```console
python -m csr2cdn.crew_endpoint_inventory --execute
```

This prompts privately for the authenticated account's PlayerID. Its JSON output can be saved or shared for schema analysis; still inspect it yourself first. The default output includes *only field names, value types and coverage counters*, plus the names of any recognized potential season/pagination metadata keys, not their values.

If you explicitly want selected numeric *candidate* stats (such as the unverified `crewRP` scalar, crew level, invites/requests, and aggregate member donation/boost counts), opt in:

```console
python -m csr2cdn.crew_endpoint_inventory --execute --show-stat-candidates
```

This adds **only** the following safe numeric previews: own-crew selected counters and min/max/sum for narrowly selected numeric fields across members. It does not print individual contributions, activity timestamps, external IDs, crew motto text, car identifiers or GCC logo values. Candidate preview units and season scope are **unverified**. Presence, null, numeric and invalid counters are reported even without this switch.

Offline inspection of an already available response triplet (also zero network calls):

```console
python -m csr2cdn.crew_endpoint_inventory --own-json own.json --members-json members.json --gcc-json gcc.json
```

Do **not** share those original JSON files: they may include account data and secrets. The CLI never writes them. Each supplied file is capped at 8 MiB.

## Data captured and not captured

- `own_crew.raw_envelope`, `.selected_payload`: sanitized field names and types; candidate presence/numeric/null/invalid counts for known native crew statistics.
- `roster.raw_envelope`, `.selected_payload`, `.member_array_container`, `.member_rows`: counts/coverage of member field keys, including possible donations, Season Pass boost, car information and optional native properties. A one-level structure census covers known nested-car containers when they are dictionaries.
- `gcc_progress.raw_envelope`, `.selected_payload`, `.score_rows`: full **bounded** schema for the already returned GCC rows, plus one-level `logo` names/types. No opaque logo values or crew IDs are included.
- `metadata_key_cues`: only names of fields suggestive of season, timestamp, page/cursor/count and boundary metadata on selected response objects and selected one-level metadata containers. Such names are **not proof** of real season selection or valid cursor behavior.
- Typed GCC progress objects now preserve `logo`, other row `extras`, and decoded payload `extras` in memory for later work; these remain omitted from their `repr` and the diagnostic output. `crew_id`, rank, score semantics are unchanged.

This is intentionally **bounded**, not a deep recursive raw JSON dump. It inspects up to 1,000 rows and 128 fields per object, limits field-name totals, filters sensitive/irregular field names, does not traverse arbitrary nested objects, and uses names/types rather than values. Any hidden/truncated field counts appear in the output. This provides a useful census while reducing accidental disclosure risks. The filter cannot guarantee that arbitrarily malicious field names are safe, so review output before sharing.

## Decision gates after the next live pass

Only promote new typed fields after comparing *actual presence and numerical meaning* with game UI/native parser evidence; particularly `crewRP`, token donations, Season Pass boost and member car/performance counters. A returned GCC `logo` object is evidence of structure, **not** a validated image URL or public asset. If a genuine season ID/time marker appears, trace its semantics before marking the current 14-day season confirmed. Do not infer complete leaderboard pagination or season scope from the 21-row GCC response.

Dev29 does not itself request a live game response. Existing Crew RP validation and remaining release blockers stay unchanged. No new game writes, Prestige tests, GitHub/PyPI publication or altered GCC request parameters were introduced.
