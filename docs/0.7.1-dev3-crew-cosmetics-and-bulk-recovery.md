# 0.7.1.dev3 — crew presentation, roster cosmetics and partial-read recovery

This is an **offline-only** development change on top of `0.7.1.dev2`.
No new game-service URL, signed contract, authentication flow or game write.
Published `v0.7.0` remains unchanged; all new data is provisional.

## Native/wire evidence and field treatment

Known from the Dev30 authorized schema inventory (CSR2 6.8.0): own-crew
`crew_logo` contains `id` and `colour`; the `tournament` object has `events`,
`extra` and `meta` child objects. Dev3 exposes a typed emblem and text-limited
motto/language. For tournaments it exposes only section presence and number
of keys, **not** actual keys or values. This does not establish the meaning of
individual events or their season identifiers.

All observed member rows contained cosmetic fields including `car_calliper_id`,
`car_interior_id`, `car_livery_id`, `car_liveryZonesSet_id`, `car_paint_id`,
`car_wheel_name`, `car_decal_flag_id`, `car_decal_number_id`,
`car_decal_number_color_id`, `car_decal_number_shape_color_id`,
`car_decal_number_zone_id`, `car_decal_numberplate_style_id`,
`car_decal_playername_state` and `car_decal_crewname_state`. Dev3 maps these
as optional **identifiers**, not decoded display names, textures or colors.
`car_tnr_setup` remains opaque: at most the fact an object exists and a
bounded field count is exposed. `license_plate_text`, `facebook_id`, player
identifiers and last-login data never enter the appearance model.

Unknown fields remain unset, booleans and floats do not turn into IDs, and a
numeric ID of zero is valid. `CrewOptionalSnapshot.from_reads` still
requires matching crew identifiers. Model representations avoid names and
motto/appearance strings; reports show coverage by default.

## Batch failure isolation

The bulk command still prepares **exactly four** reads in an authorized live
run: own crew, roster, common GCC, one experimental GCC range. It makes no
additional network calls and never retries automatically. An HTTP or other
exception from a GCC request is caught without disclosing server messages;
the remaining read still runs. A partial result prints normally and the CLI
returns **4**, so scripts cannot mistake it for full coverage. Fatal
own-crew/roster failures still return the existing error status.

### Offline dry run (zero requests)

```bash
python -m csr2cdn.crew_bulk_validation
```

### Later opt-in live batch (NOT executed for this build)

```bash
python -m csr2cdn.crew_bulk_validation --execute --top 20 --before 10 --after 10 --offset 0 --show-stat-values
```

Optional flags: `--show-members` to print names and per-member cosmetics,
`--print-gcc-entries` to print crew names/ranks/scores. Neither prints
account IDs. Review opt-in output before sharing. Offline four-reply JSON
replay is unchanged.

## Validation status

Only synthetic wire fixtures and offline test doubles exercised the new
paths. Expanded GCC range/offset behavior, optional statistic meanings,
vehicle asset identification and tournament meanings are still unverified.
Prune/fix based on one later user-authorized bulk comparison.
