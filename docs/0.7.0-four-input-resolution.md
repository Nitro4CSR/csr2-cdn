# Showdown leaderboard ID inputs — CSR2 6.8.0, dev5

**Status:** static ARM64 analysis and offline fixture tests, **not yet live verified**.
The public interface remains PlayerID + a Showdown name. Nothing in this
feature requires the caller to discover board identifiers or timestamps.

## Evidence for the four inputs

| Input | Native source | Native evidence | Python input source |
|---|---|---|---|
| Event start | `RaceEventGroup.GetTimeStart` after schedule/occurrence selection | `EventLeaderboard.GetTimeData` at `0x3388344` | Resolved `EventSchedule.ScheduleList` window or direct group `TimeStart` |
| Event duration | `GetTimeEnd` minus `GetTimeStart` | `0x33883b8`–`0x33883dc` | End minus start of the same occurrence; seconds |
| Rank direction | `EventLeaderboard.get_Info().rankingOrder` | `0x3388160`–`0x3388190`, zero vs nonzero branch | Unique matching `EventLeaderboards` definition by template ID (`asc`/`dsc`) |
| Group identifier | `RaceEventGroup.get_LeaderboardGroupIdentifier` | `0x32fb0dc`, calls first `RaceEventData.get_EventID` | `RaceEvents[0].EventID` (ordered list required) |

The normal leaderboard format from `EventLeaderboard.get_LeaderboardUniqueID`
(`0x3388010`) is `evnt-off-{offset}-dur-{duration}-hours-{direction}---{firstEventID}`.
`offset` is `((start_unix_seconds - 1514764800) % duration_seconds) // 3600`;
`duration` is `duration_seconds // 3600`. Calculations apply to the correct
occurrence; group display names and leaderboard template IDs are not server
board identifiers. A separate account/profile setting can use a different
identifier branch (`get_EventLeaderboardType == 1`); this mode is not inferred
from metadata alone and still requires client-state validation.

## Dev5 behavior

- A `ShowdownCandidate.identity_inputs` object exposes the four values and
  non-sensitive provenance. `None` means unresolved, **never zero**.
- The source of schedule windows is recorded independently from ranking-order
  and first-race-ID resolution. Duplicate schedule IDs, unknown intervals,
  ambiguous first-race ordering, missing leaderboard definitions, and
  inherited-schedule cycles are rejected rather than guessed.
- The native `RaceEventGroup.CalculateCurrentRepeatCount` calculation is
  reproduced only when a standalone group explicitly supplies absolute
  `TimeStart`, `TimeEnd`, and `TimeRepeatDuration`. The observed
  `TimeStayOnMapAfterCompletion` is respected. Inputs within two seconds of a
  repeat boundary fail closed due to the native floating-point repeat count.
- `EventScheduleDataItem` recurring schedules, experiment/account-dependent
  schedules, and other unsupported date encodings remain unresolved. A
  scheduled time window alone does not imply player eligibility or server
  leaderboard existence.
- The CLI `services --metadata-dir DIR showdowns` displays candidates and their
  four input statuses using **only local metadata**. No credentials or server
  request/signature details are emitted in diagnostic errors.

## Programmatic offline inspection

```python
from csr2cdn import ShowdownDiscovery

discovery = ShowdownDiscovery.from_json_directory('./ConfigData')
for row in discovery.list_showdowns():
    inputs = row.identity_inputs
    print(row.display_name, row.time_status, inputs.missing)
    print(inputs.time_source, inputs.ranking_source, inputs.group_source)
```

For an online metadata fetch, the existing `CSR2Services` named Showdown API
uses only PlayerID and name, and retrieves current metadata automatically.
Live compatibility and real scheduling field encodings still need verification
against a sanitized real snapshot. Do not send account identifiers or session
records; a structure-only sample of the three event metadata blocks would be
sufficient to expand unsupported schedule parsing.

## Offline verification

Synthetic regression tests cover: full four-input derivation, independent
missing-input detection, direct group timestamps, inherited intervals,
server-time Unix seconds/milliseconds, duplicate schedule mapping, one direct
repeat-cycle, unsupported recurring schedules, native integer boundaries and
ambiguous race ordering. They do not establish the live server's acceptance
of derived board names.
