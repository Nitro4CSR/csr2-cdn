# CSR2 game services — 0.7.0 first implementation (not yet released)

**Status:** `0.7.0.dev1`, offline implementation in progress; **no 6.8.0 live
server compatibility has been tested**. This is a developer preview, not a
successful 0.7.0 release. Existing 0.6.0 CDN, HUB, metadata, and snapshots APIs
are preserved. The private save-game downloader is not included and no saved
game read/write operations are exposed.

## What is implemented

| Feature | Python API | Read route and status |
| --- | --- | --- |
| Crew members and selected car metadata | `get_crew_members(crew_uid)` | `crews/viewMembers`, request type 3, native-traced |
| Classic Showdown standings | `get_showdown_leaderboard(...)` | generic event path, **provisional board route** |
| Prestige Cup standings | `get_prestige_cup_leaderboard(...)` | generic event path, **provisional board route** |
| Showdown Leagues standings | `get_showdown_leagues_leaderboard(...)` | `leaderboard/{name}/view`, type 5, native-traced |
| Showdown Leagues preview | `get_showdown_leagues_preview(name, score=...)` | `leaderboard/{name}/preview`, type 5, native-traced |
| Showdown Leagues score/rank | `get_showdown_leagues_score(name, period_offset=0)` | `leaderboard/{name}/score`, type 5, native-traced |

A method's availability in this developer preview does not guarantee the
corresponding backend supports a public read for every event. **Generic
Showdown and Prestige Cup share an *assumed* `leaderboard/{resolved-name}/view`
route**, extrapolated from the traced Showdown Leagues builder; the native
generic event method accepts an upstream-resolved `leaderboard_name` without
proving this exact route. The first live test must confirm this mapping.

Crew members include `player_uid`, `zid`, `name`, `role`, and the selected car's
identifier, PP/EP, and any extra customization fields returned by the server.
Presence, racing lobby subscriptions, mutations, and joined-lobby state
are **not implemented**, since no read contract for them has been established.

## Python usage: prepare locally and decode fixtures

```python
from csr2cdn import CSR2Services, EventCatalog, StandingRange

# Event metadata comes from caller supplied *current* data; no bundled event
# names/IDs/seasons and no assumption that event_id == leaderboard_name.
catalog = EventCatalog.from_json_file("current-event-mapping.json", ttl=300)
with CSR2Services("MY_PLAYER_ID", events=catalog) as service:
    crew_request = service.prepare_crew_members("MY_CREW_UID")
    showdown_request = service.prepare_showdown(event_id="SHOWDOWN_EVENT_ID")
    prestige_request = service.prepare_prestige_cup(event_id="PRESTIGE_EVENT_ID")
    leagues_request = service.prepare_showdown_leagues(
        leaderboard_name="RESOLVED_LEAGUE_BOARD", ranges=StandingRange.common()
    )
    # These calls neither log in nor contact the game server.
    print(crew_request.route, crew_request.params)
```

Example of the **adapter format** consumed by `EventCatalog`, not a game wire
format or built-in event catalogue:

```json
{
  "events": [
    {"event_id": "EVENT_FROM_METADATA", "kind": "showdown", "leaderboard_name": "RESOLVED_BOARD", "season": "SEASON_FROM_METADATA", "segment": "SEGMENT_FROM_METADATA", "score_unit": "trophies"},
    {"event_id": "CUP_FROM_METADATA", "kind": "prestige_cup", "leaderboard_name": "CUP_BOARD_FROM_METADATA", "instance": "INSTANCE_FROM_METADATA"}
  ]
}
```

The names above are clearly **placeholders**, not actual CSR2 event IDs.
The adapter supports multiple boards per event across season, segment,
instance, and crew scope. If a lookup is ambiguous, `EventResolutionError`
is raised rather than picking an arbitrary board. `refresh=True` bypasses the
cache and re-invokes the source. `EventCatalog.from_metadata(client,
block_names=..., zid=..., product_version=..., extract=...)` supports dynamic
metadata discovery with a caller-provided schema extractor. Block names and
event mappings are intentionally not guessed.

Use `CSR2Services.decode_crew_members(crew_uid, fixture_json)` and
`CSR2Services.decode_leaderboard(board, fixture_json)` to experiment with
sanitized recorded **JSON fixtures**. The decoders accept selected expected
field spellings and preserve other fields only in memory. They reject malformed
or missing arrays rather than reporting false empty results. Score units,
rank ties and response wrappers are provisional until live verification.

## CLI (offline by default)

```console
csr2cdn services crew CREW_UID
csr2cdn services crew CREW_UID --response-file fixture-crew.json
csr2cdn services --events-file current-event-mapping.json events --refresh
csr2cdn services --events-file current-event-mapping.json showdown --event-id EVENT_FROM_METADATA
csr2cdn services --events-file current-event-mapping.json prestige --event-id CUP_FROM_METADATA
csr2cdn services showdown-leagues --leaderboard-name RESOLVED_BOARD --top 3 --after 0 --before 0
csr2cdn services showdown-leagues --leaderboard-name RESOLVED_BOARD --player-score --offset 0
csr2cdn services showdown-leagues --leaderboard-name RESOLVED_BOARD --preview-score 600
```

Without `--execute`, commands print the validated route and parameters but
perform **zero network I/O**. With `--response-file`, the CLI decodes an
offline fixture and displays only modeled fields, not opaque extra data.
The optional `--execute` switch makes the actual HTTPS request and will only
be used during final live validation with a user-owned account, for example:

```console
csr2cdn --zid MY_PLAYER_ID services --execute crew MY_CREW_UID
```

**Do not run `--execute` yet if live testing is intentionally deferred.**
The service session is handled internally, and no credential details are
included in logs or shipped fixtures. Network requests are opt-in. No save-game downloader, uploader, or account profile route exists here.

## Known limitations to verify before 0.7.0 final

1. **Generic leaderboard backend selection:** establish the correct wire route
   for classic Showdown and Prestige Cup independently. Replace the provisional
   shared read builder if either service uses another endpoint or format.
2. **Event discovery:** identify authoritative CSR2 metadata blocks and the
   event-instance/leaderboard-name derivation from native calls. The current
   adapter is implemented, but automatic built-in discovery is not established.
3. **Result schema:** confirm wrapper keys, leaderboard rank, trophy/elapsed-time
   score units, range/offset semantics, ties, and completed-event retention.
4. **Crew data:** confirm full current-car fields and whether an independent
   crew hangout presence read exists (membership alone is not live presence).
5. **Auth and server:** validate request types, token refresh, effective
   endpoint, and authorized read behavior in CSR2 6.8.0. No raw tokens or player
   responses should be published.
6. **Release:** run Windows/Linux Python 3.9/3.13 CI; publish tag and PyPI
   distribution via the existing trusted-publish workflow *after* validation.

Offline unit tests are synthetic. They are **not** proof of server compatibility.
