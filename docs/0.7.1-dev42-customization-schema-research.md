# Dev42 — Offline customization metadata schema-shape research

## Scope and evidence

Dev41 identifies fourteen crew visual wire fields and seven **candidate** customization metadata blocks. The candidate status is not an established field-to-source join. In particular, `CarCustomizationParameters`, `CarAftermarketCustomisations`, `CarLiveriesMatrix`, `CarPresets`, `CarAdditionalVisuals`, `AftermarketConfig`, and `HypermodMaterialsConfig` have not been semantically decoded as roster cosmetic keys.

Two different source formats are intentionally separated:

1. **APK** `assets/Media/Metadata/<name>.metadata` entries are binary NMG: the existing `inspect_customization_apk` returns bounded sizes, digests and format status, not field names.
2. **Local metadata service cache** `<name>.meta` files are JSON. Dev42 samples key names and value **types** only from existing files (up to 16 items per array, depth 9, 50,000 visited nodes; 8 MiB per file), groups key syntax into broad families, and calculates SHA-256 for reproducibility. This does not mean the keys are the native APK fields.

The default redacted report contains no source values, actual JSON key names, player data, or roster model keys. A separate *opt-in* private report can show sampled key paths (up to 120 per block) but **no values**. It must be treated as private and **cannot be shared as proof of semantic mapping**. Structural counts are sample counts, never total-library record counts. The loader rejects symlinks, empty/oversized and malformed cache entries, unexpected deep nesting, pre-existing outputs, and impossible Dev41-baseline verification claims.

## Run without any optional original data

```bash
python -m csr2cdn.dev42_customization_schema_audit \
  --provenance-report dev41-field-source-provenance.json \
  --output dev42-schema-report.json
```

Expected result: seven missing-original-source statuses, Dev41 field inventory preserved, no verified native field joins. There is **nothing to decode in the Dev41 source ZIP alone** beyond the existing candidate inventory.

## Analyze a previously saved local metadata cache and/or APK

```bash
python -m csr2cdn.dev42_customization_schema_audit \
  --provenance-report dev41-field-source-provenance.json \
  --metadata-cache-dir ./saved-metadata-cache \
  --apk ./existing-local-game.apk \
  --output dev42-schema-report.json
```

This does not create, authenticate, or download metadata. It reads only the seven allowlisted block files. It does not assert database-version identity between a local APK, cached JSON and the Dev41 CDN evidence; their exact versions should be established separately.

To inspect field **names** in your Work session, explicitly request the separate private file:

```bash
python -m csr2cdn.dev42_customization_schema_audit \
  --metadata-cache-dir ./saved-metadata-cache \
  --output dev42-schema-report.json \
  --private-key-paths-output dev42-private-key-paths.json
```

The private report is local-only, new-file-only and permission-restricted where supported. Never upload private caches or player tokens to a public service. There are **zero** network and gameplay requests.

## What would justify new joins?

A native schema that identifies the target field and its foreign-key/reference rules, corroborated on independent source records and with eligibility semantics checked. Matching names, matching numbers, hash equality, CDN presence, or a key's spelling alone are insufficient. The existing `car_paint_id` values `0` (8 occurrences; operator-approved *Transparent* display alias) and `15` (one occurrence) remain evidence from Dev38/Dev39, not newly resolved in Dev42. No production mapping changes are made.
