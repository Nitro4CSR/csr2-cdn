# Dev30 — existing crew read data: field semantics, timing and cross-checks

**Status:** offline-prepared diagnostic, **not** an authenticated Dev30 result. No additional routes, read parameters, pages, authentication changes, game writes, or raw reply persistence.

## Evidence hierarchy

This implementation is based on (1) the supplied Dev29 **live** field-and-type inventory for October 16, 2026; (2) native fields/methods already traced in the supplied CSR2 6.8.0 APK; and (3) Dev27's authorized near-contemporaneous member-vs-GCC equality. A native field declaration alone does **not** establish a specific wire key or the values that the backend sends. Numeric names alone do **not** establish units, season scope or the truth of a conversion.

### Three unchanged read contracts

- `crews/checkUserCrew`: observed real own-crew keys include `crew_rp`, `crew_level`, `crew_level_base`, `crew_level_threshold`, `crew_garage_value`, `crew_career_earning`, `crew_rr_point`, `members`, `max_members`, `total_invites`, `total_requests`, `crew_logo`, `tournament`. Dev29's older numeric preview searched different camelCase spellings; Dev30 recognizes the observed spellings **and** retains existing older candidates. `crew_rp` is **not** automatically classified as seasonal Crew RP.
- `crews/viewMembers`: observed 29 member rows include `cc_contrib`, `career_earning`, `cash_donated`, `collections_rank`, `season_pass_rp_boost`, `car_pp`, `car_ep`, `car_gacha_config`, and `car_tnr_setup`. Dev30 reports aggregate numeric candidates and one-level nested schema for the two car configuration objects. Presence/coverage of `TokenDonated_season` is checked if ever returned, but the Dev29 live inventory **did not** report that member field. External IDs, member names and detailed activity timestamps are not printed.
- `leaderboard/crew-champs-v2/viewcrew`: 21 observed rows containing crew identity, rank, score and `logo` (nested `id` and `colour`). Top-level metadata keys `end_time`, `time_left`, `cardinality`, `bucket`, `tier` were **confirmed present**, but the Dev29 inventory did not disclose their actual values.

### Native interpretation limits

- Prior APK trace resolves `PlayerCrewMember.FromJSONDict` reading `cc_contrib` into `RP_season`, and separate `RemoteCrewInfo` results reading `cc_rp` into `CrewRP_season`. They are different response shapes from the live GCC **progress** `scores` rows.
- APK type metadata for `GrandCrewChampionshipResults` declares `EndTime`, `TimeLeft`, `Cardinality`, `Tier`, and `Bucket`. Those names support a **hypothesis** that the observed GCC envelope fields represent a timed championship window/grouping. This alone does not prove that `end_time` is a Unix timestamp, `time_left` is seconds, `cardinality` is a total leaderboard count, or `bucket` / `tier` are season selectors. Without numeric values and a native units trace, no season ID, 14-day bound, reset or paging interpretation can be certified.
- The APK `CheckUserCrewResponse` metadata declares crew progress / cumulative statistics and a tournament payload. The **observed** snake_case JSON spelling is supported by the Dev29 inventory; one-to-one correspondence with particular native member offsets is not independently proven by that inventory.

## Dev30 additions

1. Expanded *exact* own-crew / roster numeric allowlists. Default still prints **counts and types only**; explicit `--show-stat-candidates` prints own-crew numeric scalar candidates and *aggregate-only* member statistics (including `cc_contrib` total), not individual values.
2. GCC `timing_and_scope` report shows presence/types of all five confirmed envelope fields. `--show-gcc-metadata` opts into bounded integer counters and safe short ASCII strings for `bucket` / `tier`. It also **hypothesizes** a Unix-seconds `end_time` and duration-seconds `time_left`, showing a candidate implied server time and (during a live run) delta against read completion time **only when values are numerically plausible**. The report always says season ID and time-left units are unverified. The correlation is evidence for future interpretation, not certification.
3. Expanded **one-level-only** censuses for `tournament`, `crew_logo`, `car_gacha_config`, `car_tnr_setup`, and existing GCC `logo`, with bounded names/types only, no nested values.
4. `rp_cross_read_comparison` explicitly keeps **three distinct quantities**: own `crew_rp`, sum of typed roster `cc_contrib` and exact-ID-matched GCC `score`. Optional numeric deltas are suppressed unless the returned roster count matches own-crew `members` (or `memberCount` in older fixtures), member identities are distinct, all typed contributions are valid and GCC returns exactly one own-crew match. During a live run a read-completion gap over 30 seconds or inverted completion order also prevents a delta. This remains a **sequential, non-atomic** consistency comparison, not proof of any pair sharing seasonal semantics.
5. No new typed release-facing property is added for unverified `crew_rp`, `end_time`, `bucket`, or `tier`. These diagnostics do not change the known `CrewRPSnapshot` or verified member contribution source.
