# 0.7.1.dev7 — Offline native-label extraction adapters

## Evidence and limitations

The local CSR2 6.8.0 APK's IL2CPP metadata contains the symbols
`TranslationFile`, `TranslationEntry`, `GetRootAsTranslationFile`,
`TranslationsByKey`, `ShortName`, `MediumName`, and `LongName`. This is
credible evidence that the game has a FlatBuffers translation model; the
binary field numbers, translation-file location, exact DB-name relationship,
and file identity **remain unverified**. No native translation asset or
current Metadata CDN response was fetched in Dev7.

The game's Metadata CDN supplies blocks through `MetadataCache`; unlike
binary files embedded in an APK, cached `.meta` blocks are JSON-decoded
by the existing client and can have independently refreshed CDN hashes.
The seven known customization-related block names provide *candidate*
sources for visual codes. Their native record paths and slot-to-label
semantics are **not yet established**. The JSON keys in examples below
are synthetic test fields, not claims about a live CSR2 block.

Dev7 therefore adds **explicit-layout, strict offline decoders** rather
than silently assuming a game schema. It does not automatically sync the
Metadata CDN, does not require credentials and does not issue gameplay reads.

## Inspect a local metadata cache without printing private contents

```sh
python -m csr2cdn.native_source_validation --metadata-cache-dir ./metadata
```

This returns block presence, hash availability, aggregate JSON types and
sizes, with **no values or keys** by default. Add `--show-field-names`
for bounded, opt-in property-key introspection. Never publish a report that
contains private source identifiers without reviewing it.

Use an explicitly observed block schema to make a visual layout document:

```json
[
  {
    "format": "csr2cdn.visual-json-layout.v1",
    "block": "CarAdditionalVisuals",
    "records_path": ["paintOptions"],
    "model_field": "model", "code_field": "id", "label_field": "label",
    "slot": "paint"
  }
]
```

**This is an illustrative synthetic layout.** Do not apply it to a real cache
until the actual CDN response confirms those names and the result is checked
against in-game cosmetics. Supported slots are those in `SLOT_FIELDS`.

Given a *verified* layout file and a hashed cached JSON block:

```sh
python -m csr2cdn.native_source_validation \
  --metadata-cache-dir ./metadata \
  --visual-layout-json visual-layouts.json \
  --output-visual-json visual-names.json
```

The normalized output is compatible with `GameVisualLibrary.from_manifest`.
An unknown path, missing hash, duplicate key, wrong type, oversized data or
unsupported slot is an error. Files are never overwritten.

## Decode a locally held translation FlatBuffer with an evidenced schema

A layout manifest supplies **field indices**, not names. For example:

```json
{
  "format": "csr2cdn.translation-flatbuffer-layout.v1",
  "entries": 0,
  "model_key": 0, "short": 1, "medium": 2, "long": 3
}
```

**These integers are synthetic fixture indices, not verified CSR2 values.**
The reader checks FlatBuffers vtables, relative offsets, vectors, UTF-8,
label limits and duplicate keys. It will reject an incompatible binary.
Use `--expected-model-key` to require exact known identifiers before export:

```sh
python -m csr2cdn.native_source_validation \
  --translation-file ./translations.flat \
  --translation-layout-json ./verified-layout.json \
  --expected-model-key Abarth_500_2014 \
  --output-translations-json ./car-names.json
```

The normalized output can be fed to `GameCarTranslations.from_manifest`.
Users choose `SHORT`, `MEDIUM` (default), or `LONG`, with no hidden fallback.
**Successfully decoding a synthetic FlatBuffer does not validate field
indices against the real game.** Names require genuine source and UI checks.

## Bulk test wiring

The offline-first `crew_bulk_validation` CLI accepts additional opt-in inputs:

* `--translation-flatbuffer` and `--translation-layout-json` together,
  instead of `--car-translations-json`.
* `--visual-cache-layout-json` with `--metadata-cache-dir`, instead of
  `--visual-library-json`.

Both decode locally. The existing authorized live batch stays at **four
read-only game requests**; no metadata CDN requests are automatically added.
All enriched-label features remain candidate-level until compared to the UI.

## Remaining gates

1. Acquire actual game translation FlatBuffer(s) from the correct asset source.
2. Determine field indices using a real file and independently verify model
   keys and all three display variants.
3. Inspect current JSON Metadata CDN visual-code blocks to determine real
   array paths and source-field mappings.
4. Test representative vehicle/paint/wheel/livery/decal mappings offline,
   then bundle them with the planned 0.7.1 live comparison and prune unsupported ones.

No game/account writes, metadata CDN reads, GitHub changes or PyPI publication
occurred during Dev7.
