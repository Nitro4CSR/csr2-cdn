# Dev31 — rehearsal for 14-day Crew RP season rollover

**Offline implementation; no authenticated Dev31 live test.** This is a response to the operator's expected server behavior: at the boundary, member `cc_contrib` and the crew's **seasonal** GCC progress `score` reset to zero. It does not claim a server reset occurred on October 22, 2026, or that the envelope contains an explicit season ID.

## Proven data-source relationships (prior independent live reports)

- `crews/viewMembers`: all 29 `cc_contrib` fields were numeric in the authorized Dev30 reading.
- `leaderboard/crew-champs-v2/viewcrew`: exact own-crew ID match and GCC `score` equalling the complete member contribution sum in that reading; requests **0.230 seconds** apart. The ranked window is not the complete leaderboard.
- `crews/checkUserCrew`: own-crew `crew_rp` *not* equal to the GCC contribution score; unit/lifetime interpretation still unverified. The crew garage value matched the summed member garage values in the preceding investigation.
- GCC `end_time=1792663200` converts to **2026-10-22 10:00 UTC**. `time_left=496558` gives an implied read time within **0.923 seconds** of the recorded time. This supports a Unix-seconds representation and a championship end, but does not independently validate each reset or the season ID.

## What Dev31 implements

1. `GCCSeasonTiming.from_gcc` reads the **already available** GCC response envelope, checks strictly typed `end_time`/`time_left`, and reports a candidate end, operator-assumed 14-day start and clock correlation. No new requests are needed and no fixed current season ID is installed. A plausible end/left pair is not an authenticated season identifier.
2. `CrewSeasonTransition.between(previous, current)` compares two existing `CrewRPSnapshot`s for a **same-crew, chronological, approximately 14-day** advanced GCC end, complete member roster, exact-ID matched GCC score and observed zeros. It independently tracks the own-crew `crew_rp` and garage-value counters and does **not** call either of them seasonal Crew RP. A one-hour tolerance accommodates daylight-saving shifts for 14 local-calendar-day cycles (an assumption, not a proven cadence).
3. Only actual zero values can create `zero_reset_observed_in_supplied_snapshots=True`. If players have already started earning RP in the new season, a nonzero score is valid; `zero_reset_not_observed_may_have_resumed_earning` is diagnostic, not an error. The implementation never forces a reset or carries prior-season RP into the new snapshot.
4. `CrewRPSnapshot` marks non-atomic member/GCC reads crossing a candidate season boundary as incomparable; if a previous plausible end is known, that boundary is preferred over a computed 14-day start. Incomplete rosters, wrong IDs, stale responses or failed timing also cannot fabricate a zero-reset observation.
5. Larger own-crew statistics are preserved internally under `own_crew_rp_unverified` and `own_crew_garage_value_unverified`; summaries omit them by default unless `show_own_crew_stats=True` is explicitly supplied. No IDs, names or authentication secrets are printed in summary output.

## Run the synthetic reset rehearsal (zero network)

```bash
python -m csr2cdn.crew_season_validation
python -m csr2cdn.crew_season_validation --simulate
```

The demonstration uses **synthetic** member IDs, 29 accounts, fictional RP values, a mocked boundary of 2026-10-22 10:00 UTC and an advanced end exactly 14 days later. It confirms that *code logic handles the reset-to-zero contract*, **not that the live server has reset**. The implementation includes separate tests for a plausible DST one-hour boundary shift.

To compare any two authenticated snapshots in a future run, use the same established read-only service method `CSR2Services.get_crew_rp_snapshot(previous=old_snapshot)` and then `CrewSeasonTransition.between(old_snapshot, new_snapshot)`. No additional route, authentication method or game-state mutation is introduced. A run now cannot observe a future actual reset; no automated polling is installed.

## Remaining uncertainties

- No server-certified season ID, start timestamp or observed rollover.
- A reset might occur between the sequential roster and leaderboard reads, or a zero-score crew might temporarily be absent/unranked in the GCC window. Those cases must be handled as incomplete or noncomparable instead of being labeled a verified reset.
- Once players have scored again, a genuine rollover can have nonzero values. A missing exactly-zero observation is not evidence of failure.
- UTC time between boundaries can differ by one hour when local daylight-saving rules apply. The server's actual schedule basis has not been established.
- Final 0.7.0 publication is still blocked by season lifecycle/UI, Prestige, pagination and cross-platform CI requirements.
