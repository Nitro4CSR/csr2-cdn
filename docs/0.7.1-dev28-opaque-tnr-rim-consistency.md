# Dev28 — offline TNR opaque trailer screening and rim consistency

## Strict input boundary

Dev28 is **package-only, offline-first source analysis**. The Dev27 archive contains source code and synthetic test fixtures, but no original saved Dev24 roster, original Tuner Stars native library bytes, or player data. All concrete Dev28 tests use synthetic UnityFS bundles. No authenticated gameplay calls, CDN traffic, asset downloads, or network requests were made. The actual numeric identifiers of the ten unmatched paint **entries** and one unmatched interior **entry** are **not** recoverable; those are entry counts, not necessarily distinct IDs.

The proven Dev23 TNR primary decoder, strict production source loader, and Dev24 comparison and gameplay probe are unchanged. The Dev26 isolated cross-library comparison loader remains isolated, and Dev27 standalone rim decoder remains unchanged. No source labels have been promoted to trusted gameplay mappings.

## New counters: TNR post-primary bytes

`audit_tnr_eligibility_source()` still requires a uniquely located, canonically validated TNR primary array and a second independent walk. After finding the array end it now calls `summarize_opaque_tnr_tail(node[end:])`, which scans **only the trailing bytes** for candidates resembling four-byte-aligned length-prefixed, printable ASCII Unity strings with zero padding and lengths 4–160 bytes. It reports aggregate candidate counts, distinct candidate byte-sequence counts, length buckets, and occurrences matching the **syntactic** TNR model token pattern. It does not return content, numeric IDs, source labels, car keys, paths, or byte fingerprints.

This is strictly a **heuristic over opaque bytes**: length-prefixed candidates can occur coincidentally inside serialized values. The data is not assigned to schema fields, compatibility arrays, source-ID lookup tables, or vehicles; it cannot prove any `IncludeToCar` meaning, determine eligibility, or resolve a cosmetic label. Maximum tail size is 256 KiB. Invalid input fails closed. It is possible for valid non-ASCII Unicode strings or non-aligned fields to be missed; that is not evidence of their absence.

## New counters: native rim reference integrity

`audit_tuner_rim_source()` continues to validate the entire local original library with the canonical decoder and uniquely locate the full array. The new aggregate-only checks count:

- Blank and duplicate per-row `CompatibleCars` entries, and the number of rim rows with repeated compatible-car names.
- Distinct nonempty `CompatibleCars` strings not represented among root `CarNames`, and distinct nonempty root `CarNames` not referenced by rim rows.
- Blank and repeated root `CarNames`, blank `DefaultRim` strings, and distinct nonblank `DefaultRim` strings not matching a primary rim name.

A mismatch may be intentional under game semantics not yet understood. No rule is inferred for missing or unmatched entries, nor is root-array positional ordering promoted into a verified car/default-rim relationship. No raw strings are disclosed.

## Corrected offline wheel boundary check

The Dev25 **offline diagnostic** `assess_wheel_evidence()` previously treated `MODEL_Wheelbase` and `MODEL_Wheels` as possible wheel bundles for `MODEL`, because it accepted a raw `startswith('MODEL_Wheel')`. It now requires an exact whole `MODEL_Wheel` filename token or `_` / `.` separator immediately after it, matching the Dev27 asset-index lexical convention. This is an **offline false-positive correction** only; it does not alter the Dev24 roster probe or establish a roster wheel-name join. Asset names remain suppressed from reports.
