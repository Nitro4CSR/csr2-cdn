# Dev25 GCC progress `scores` response investigation (unreleased)

## Evidence (2026-10-16)

The authorized dev24 6.8.0 GCC progress read to the experimental APK-default `leaderboard/crew-champs-v2/viewcrew` route returned JSON (no reported HTTP rejection). The live diagnostic saw one `scores` array holding **21 dictionary rows**, with **zero top-level `cc_rp` entries**. The response itself was not retained in the provided live-output artifact. The 21 rows cannot be assumed to be 21 crew standings: no crew identity, current-season Crew RP, rank, pagination or season identifier was decoded.

The compiled `FetchGrandCrewChampionshipResponse..ctor` at RVA `0x350864c` uses `FillFromJsonList` at `0x350592c`, whose crew-row parser is `RemoteCrewInfo.FromJSONDict` (`cc_rp` -> `CrewRP_season`, `crew_rank` -> crew rank). This native **results** code path is not evidence that the separate **current progress** `scores` array uses the same record schema. The original dev24 decoder conflated the two by trying a results-row decoder on the progress response. Dev25 keeps that distinction explicit.

## Changed behavior

`csr2cdn.crew_rp_verification` now recognizes a `scores` array as an **unverified progress-score shape** and prints a bounded field/type census across up to 1000 rows, including whitelisted nested object fields. Numeric values, player/crew IDs, raw JSON, tokens and names are **not** printed by default. No generic `score` field is promoted to seasonal crew RP or rank; the 14-day season and the expected 37,448,821 RP / rank 257 snapshot remain unverified.

Two further explicitly opted-in flags are available:

* `--gcc-show-schema-keys` prints up to 64 syntactically safe row key names and their type counts, filtered to exclude token/auth/secret/session/etc. It never prints unknown property values.
* `--gcc-print-score-candidates` prints up to 50 candidate rows with *whitelisted* numeric `score`, `value`, `points`, `cc_rp`, rank/position fields, limited nested `crew`, `entity`, or `score` fields, and printable name hints. **Each value is labeled `_unverified` and is not treated as Crew RP or leaderboard rank.** It does not print account or crew ID fields or raw responses. As in dev23/dev24, names and scores are personal crew data; keep logs private.

For a single, opt-in **read-only** current progress check that skips the member roster:

```console
python -m csr2cdn.crew_rp_verification --execute --print-member-values --gcc-live --gcc-only --gcc-show-schema-keys --gcc-print-score-candidates --reference-total 37448821 --reference-rank 257 --season-note "Manthey 911 Prestige Cup"
```

`--print-member-values` remains the explicit printing acknowledgement required by the existing CLI, although `--gcc-only` skips the roster. Run in an interactive terminal; PlayerID is entered privately. Only one GCC read is performed in addition to the own-crew identification read (subject to the client's existing authentication/401 retry behavior). No account writes or speculative endpoint fallbacks. A new set of RPC endpoints or active-season selectors has not been added.

Alternative: if you have a locally captured *actual* response JSON, inspect it fully offline:

```console
python -m csr2cdn.crew_rp_verification --gcc-response-json captured.json --gcc-show-schema-keys --gcc-print-score-candidates
```

The CLI returns exit **3** for unrecognized or unverified GCC shapes. This is intentional: it distinguishes a successful *diagnostic read* from successful **crew-standings decoding**. Native-format `results` rows remain handled by the existing GCC decoder. Structural fields `scores` are not silently relabeled as `results`.
