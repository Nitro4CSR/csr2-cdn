# Android ASTC caliper and colour libraries — 0.7.1.dev14

## Source evidence and record layouts

Inspected the user-supplied original `CarCalliperLibrary.ASTC.1004` and
`CarColorLibrary.ASTC.594` through the existing verified UnityFS/LZMA reader.
Both are single-node UnityFS v8 serialized Unity 2021.3.16f1 objects with
visible type-tree declarations. Counts and byte layouts were checked against
complete record arrays, not inferred from guessed display values.

- **CarCalliperLibrary:** `CarCallipers` array: 384 records. Per record:
  `ID: int32`, `Name: Unity string`, `Zone1DiffuseTint: 4 x float32`,
  `Origin: int32`, `CashPrice: int32`; all 384 IDs distinct, names nonempty.
- **CarColorLibrary:** `CarColors` array: 11 records. Per record:
  `ID: int32`, `NameID: Unity string`, `color: 4 x float32`.
  All 11 IDs are distinct. ID 9 has `NameID=""` and is omitted from named
  exports; the remaining ten are labeled. An `isModified` type-tree field
  belongs to the containing serialized type; it is not a per-entry name.

SHA-256 of each original input is retained on exported `VisualCodeName` records.
The original binaries are **not** included in the Python package or test fixtures.

## Bound versus unbound meanings

The observed crew roster exposes `car_calliper_id`, which is enough to bind
caliper names via `CrewMemberVehicle.with_visuals()`. The decoded palette
IDs have *not* been shown to correspond to `car_decal_number_color_id` or
`car_decal_number_shape_color_id` in a live response, so the palette is exposed
only as explicit `GameVisualLibrary.match(model, "color", numeric_id)`.
Unmatched and blank records stay unresolved. No additional game or CDN reads.

## Verification limits

These exact layouts are verified for the two uploaded Android ASTC versions.
Future versions, iOS High asset variants, and real roster join coverage
remain unverified. The four-request gameplay bulk test is still deferred.
